## Virtual Memory
Virtual Memory는 프로세스 전체가 물리 메모리에 적재되지 않아도 실행될 수 있도록 하는 기법이다. 이를 통해 프로그램은 실제 물리 메모리의 크기보다 더 큰 메모리를 사용하는 것처럼 동작할 수 있다. 

가상 메모리는 논리적 메모리와 물리적 메모리를 분리하여 추상화한다. 프로그램은 연속적이고 매우 큰 메모리 공간을 사용하는 것처럼 보이지만, 실제로는 그중 필요한 부분만 물리적 메모리에 올라가고 나머지는 보조기억장치에 저장된다. 필요한 시점에만 메모리로 불러오는 방식을 통해 메모리 사용의 효율성을 높일 수 있다.

가상 메모리는 여러 프로세스가 동일한 파일이나 라이브러리를 효율적으로 공유할 수 있게 해준다. 공통 코드 영역은 하나만 메모리에 적재하고 여러 프로세스가 이를 함께 사용할 수 있기 때문에 메모리 낭비를 줄일 수 있다. 더 나아가 프로세스 생성 시에도 모든 메모리를 즉시 복사하지 않고, 실제로 수정이 발생하는 시점에만 복사하는 방식(Copy-on-Write)을 사용하여 시스템 성능을 향상시킨다.

### Virtual Address Space
Virtual Address Space는 프로세스가 메모리에 저장되어 있다고 인식하는 논리적(가상) 메모리의 구조를 의미한다. 이는 실제 물리적 메모리 배치와는 무관하게, 프로세스의 관점에서 보이는 메모리의 모습이다.

일반적으로 가상 주소 공간은 특정 논리적 주소, 보통 주소 0번부터 시작한다. 그리고 프로세스는 자신이 연속적인(Contiguous) 메모리 공간을 사용하고 있다고 인식한다. 즉, 프로그램 입장에서는 코드, 데이터, 힙, 스택 등이 하나의 큰 연속된 메모리 공간 안에 존재하는 것처럼 보인다.

하지만 실제 물리적 메모리에서는 이러한 주소들이 연속적으로 배치되지 않을 수 있다. 운영체제는 페이지 테이블과 같은 메커니즘을 사용하여 가상 주소를 물리 주소로 변환하고, 이를 통해 프로세스가 연속적인 메모리를 사용하는 것처럼 보이게 한다.

### Page Sharing
Virtual memory는 페이지 공유(page sharing)를 통해 두 개 이상의 프로세스가 파일이나 메모리를 함께 사용할 수 있도록 한다. 운영체제는 동일한 물리적 페이지를 여러 프로세스의 가상 주소 공간에 매핑함으로써, 각 프로세스가 마치 자신의 메모리인 것처럼 해당 데이터를 사용할 수 있게 한다.

여러 프로그램이 동일한 라이브러리를 사용할 경우, 그 라이브러리 코드를 물리 메모리에 한 번만 올려두고 여러 프로세스의 가상 주소 공간에 연결(mapping)할 수 있다. 

또한 공유 메모리(shared memory) 기법을 사용하면 프로세스 간 통신(IPC)도 효율적으로 수행할 수 있다. 이 경우, 동일한 물리 페이지를 여러 프로세스가 접근함으로써 데이터를 빠르게 주고받을 수 있다.


##  Demand Paging
실행 가능한 프로그램이 보조기억장치(secondary storage)에 저장되어 있다고 가정하면, 이 프로그램을 실행하려면 먼저 메모리에 적재되어야 한다. 한 가지 방법은 프로그램 전체를 물리적 메모리에 한 번에 올리는 것이다. 그러나 이 방식은 실제로 사용되지 않는 부분까지 모두 메모리에 적재하게 되므로 메모리 공간이 낭비될 수 있다.

Demand Paging은 프로그램의 모든 내용을 미리 메모리에 올리는 대신, 실행 과정에서 실제로 필요한 페이지들만 그때그때 메모리에 적재하는 방식이다. 

Demand Paging 기반의 가상 메모리에서는, 어떤 페이지가 실행 도중 처음 참조될 때에만 해당 페이지가 보조기억장치에서 물리적 메모리로 로드된다. 만약 필요한 페이지가 메모리에 없다면 페이지 폴트(page fault)가 발생하고, 운영체제가 해당 페이지를 디스크에서 읽어와 메모리에 적재한 뒤 프로그램 실행을 계속한다.

이 방식은 메모리 사용 효율을 크게 향상시키며, 물리적 메모리보다 큰 프로그램도 실행할 수 있도록 해준다.

Demand Paging의 기본 개념은 다음과 같다. 프로세스가 실행되는 동안, 모든 페이지가 동시에 물리적 메모리에 존재하는 것은 아니다. 일부 페이지는 현재 메모리에 적재되어 있고, 나머지 페이지는 보조기억장치(secondary storage)에 저장된 상태로 남아 있다. 

> 프로세스는 실행 중에 필요한 페이지만 메모리에 올라와 있게 된다.

어떤 페이지가 메모리에 존재하는지 구분하기 위해 **valid–invalid bit 기법** 이 사용된다. 각 페이지 테이블 엔트리에는 하나의 비트가 포함되어 있으며, 이 비트는 해당 페이지의 상태를 나타낸다.

- valid 비트는 해당 페이지가 유효한 주소이며 현재 물리적 메모리에 적재되어 있음을 의미한다.
- invalid 비트는 해당 페이지가 아직 메모리에 올라와 있지 않거나, 해당 주소 자체가 유효하지 않음을 의미한다.

CPU가 어떤 페이지에 접근하려고 할 때 그 페이지의 비트가 invalid로 설정되어 있다면, 페이지 폴트(page fault)가 발생한다. 그러면 운영체제가 해당 페이지를 보조기억장치에서 메모리로 가져온 뒤, 페이지 테이블을 갱신하고 프로그램 실행을 다시 이어서 수행한다.

### The procedure for handling the Page Fault
Page Fault를 처리하는 절차는 다음과 같다.

1. 운영체제는 해당 프로세스의 내부 테이블을 검사하여 그 메모리 참조가 유효한 접근인지, 아니면 잘못된(불법적인) 접근인지를 확인한다.
    - 만약 잘못된 메모리 접근이라면 해당 프로세스는 즉시 종료된다.
    - 주소 자체는 유효하지만 해당 페이지가 현재 메모리에 존재하지 않아 발생한 페이지 폴트라면, 운영체제는 그 페이지를 메모리로 적재하는 과정을 진행한다.

2. 운영체제는 사용할 수 있는 빈 프레임(free frame)을 찾는다. 이는 보통 free-frame 리스트에서 하나를 가져오는 방식으로 이루어진다. 
    - 만약 빈 프레임이 없다면, 페이지 교체(page replacement) 알고리즘을 통해 기존 페이지를 하나 내보내야 한다.

3. 빈 프레임이 확보되면, 운영체제는 보조기억장치에서 필요한 페이지를 읽어와 해당 프레임에 적재하도록 I/O 작업을 스케줄링한다. 디스크 읽기 작업이 완료되면, 내부 테이블과 페이지 테이블을 수정하여 해당 페이지가 이제 물리적 메모리에 존재함을 표시한다. 이때 valid 비트도 함께 갱신된다.

4. 모든 과정이 끝나면, 페이지 폴트로 인해 중단되었던 명령어를 다시 실행한다.

###  PureDemand Paging
Pure Demand Paging은 페이지가 실제로 필요해지기 전까지는 절대로 메모리로 가져오지 않는 방식이다. 즉, 어떤 페이지도 미리 적재하지 않고, 오직 참조되는 순간에만 메모리에 로드한다.

프로세스를 시작할 때 물리적 메모리에 아무 페이지도 올라와 있지 않은 상태로 실행을 시작할 수 있다. 운영체제가 해당 프로세스의 첫 번째 명령어 주소로 명령어 포인터(instruction pointer)를 설정하면, 그 순간 해당 페이지는 아직 메모리에 없기 때문에 페이지 폴트(page fault)가 발생한다.

페이지 폴트가 발생하면 운영체제는 보조기억장치에서 해당 명령어가 포함된 페이지를 읽어와 메모리에 적재한다. 이후 페이지 테이블을 갱신하고, 중단되었던 명령어 실행을 다시 시작한다. 그 다음에 필요한 다른 페이지들도 동일한 방식으로, 실제로 참조되는 시점에 하나씩 메모리에 올라오게 된다.

> Pure Demand Paging은 필요한 페이지만 적재함으로써 메모리 사용을 극도로 효율화하지만, 실행 초기에 많은 페이지 폴트가 발생할 수 있다는 특징이 있다.

### Locality of Reference
Locality of Reference(참조의 지역성)는 프로그램이 메모리를 접근하는 방식에 일정한 패턴이 있다는 개념이다. 

프로그램이 매 명령어 실행마다 새로운 여러 페이지를 계속해서 참조한다면 한 명령어당 여러 번의 페이지 폴트가 발생할 수도 있다. 이런 경우 시스템 성능은 크게 저하될 것이다.

그러나 실제로 실행 중인 프로그램들을 분석해 보면 이러한 극단적인 상황은 거의 발생하지 않는다. 대부분의 프로그램은 특정 시간 동안 제한된 범위의 메모리 영역을 반복적으로 참조하는 경향을 보인다. 이것이 바로 참조의 지역성(Locality of Reference)이다.

지역성은 크게 두 가지 형태로 나타난다.

1. 시간적 지역성(temporal locality)으로, 최근에 접근한 데이터나 명령어를 가까운 미래에 다시 사용할 가능성이 높다는 특성이다.
2. 공간적 지역성(spatial locality)으로, 어떤 주소를 접근하면 그 주변 주소들도 곧 접근될 가능성이 높다는 특성이다.

이러한 지역성 덕분에, 한 번 메모리에 적재된 페이지는 일정 시간 동안 계속 활용될 가능성이 크다. 따라서 Demand Paging 방식에서도 비교적 적은 페이지 폴트로 효율적인 실행이 가능하며, 전체 시스템 성능 역시 합리적인 수준으로 유지될 수 있다.

데이터 구조와 프로그램 구조를 신중하게 설계하면 코드와 데이터의 지역성(locality)을 향상시킬 수 있다. 즉, 메모리 상에서 서로 가까운 위치에 있는 데이터들을 함께 사용하도록 구성하거나, 실행 흐름이 특정 구간에 집중되도록 작성하면, 프로그램은 제한된 범위의 메모리를 반복적으로 참조하게 된다.

지역성이 높아지면 이미 메모리에 적재된 페이지를 다시 사용할 가능성이 커지므로 페이지 폴트(page fault)의 발생 빈도가 줄어든다. 결과적으로 보조기억장치 접근이 감소하고, 디스크 I/O 비용이 줄어들어 전체 시스템 성능이 향상된다.

효율적인 자료구조 선택과 메모리 접근 패턴을 고려한 프로그래밍은 가상 메모리 환경에서 매우 중요하며, 이는 단순한 코드 최적화를 넘어 시스템 성능에 직접적인 영향을 미치는 요소라고 할 수 있다.

###  Hardware Support to Demand Paging
- page table: 각 페이지가 현재 메모리에 존재하는지 여부를 구분할 수 있어야 한다. 이를 위해 페이지 테이블 엔트리에는 valid–invalid 비트가 포함된다. CPU가 invalid로 표시된 페이지에 접근하면 페이지 폴트가 발생하고, 운영체제가 이를 처리하게 된다.

- Secondary memory(swap space): 보조기억장치(secondary memory), 즉 스왑 공간(swap space)이 필요하다. 이 공간은 현재 메인 메모리에 존재하지 않는 페이지들을 저장하는 역할을 한다. 일반적으로 고속 디스크나 NVM(Non-Volatile Memory) 장치가 사용된다. 페이지 폴트가 발생하면 운영체제는 이 보조기억장치에서 필요한 페이지를 읽어와 물리적 메모리에 적재한다.


### Instruction Restart
Instruction Restart는 Demand Paging에서 매우 중요한 요구 사항이다. Demand Paging이 정상적으로 동작하려면, 페이지 폴트(page fault)가 발생한 이후에도 해당 명령어를 정확히 다시 실행할 수 있어야 한다.

페이지 폴트가 발생하면, 운영체제는 인터럽트(트랩)를 통해 현재 실행 중이던 프로세스를 일시 중단시키고, 그 시점의 프로세스 상태를 저장한다. 이 상태에는 레지스터 값, 조건 코드(condition code), 프로그램 카운터(PC, instruction counter) 등 실행에 필요한 모든 정보가 포함된다. 이러한 정보를 보존함으로써, 페이지가 메모리에 적재된 후 프로세스를 정확히 동일한 위치와 상태에서 다시 시작할 수 있다.

만약 명령어를 가져오는 과정(instruction fetch)에서 페이지 폴트가 발생했다면, 해당 페이지를 메모리에 적재한 후 동일한 명령어를 다시 가져오면 된다. 반면, 명령어는 이미 가져왔지만 피연산자(operand)를 읽는 도중 페이지 폴트가 발생했다면, 페이지를 적재한 뒤 명령어를 다시 가져오고 해독(decode)한 다음, 피연산자를 다시 읽는 과정을 수행한다.

> Instruction Restart 기능은 페이지 폴트가 발생하더라도 프로그램이 오류 없이 정상적으로 이어서 실행될 수 있도록 보장한다

### Free Frame List
Free Frame List는 페이지 폴트(page fault)가 발생했을 때 필요한 페이지를 물리적 메모리에 적재하기 위해 사용되는 관리 구조이다. 페이지 폴트가 발생하면 운영체제는 보조기억장치에 있는 해당 페이지를 메모리로 가져와야 하며, 이를 위해 사용할 수 있는 빈 프레임이 필요하다.

운영체제는 free frame list를 유지하고 있다. 이는 현재 사용되지 않고 비어 있는 물리적 프레임들의 목록으로, 페이지 폴트가 발생하면 이 목록에서 하나의 프레임을 할당하여 새 페이지를 적재한다. 이렇게 함으로써 페이지 요청을 신속하게 처리할 수 있다.

free frame은 페이지 폴트 상황뿐만 아니라, 프로세스의 스택(stack)이나 힙(heap) 영역이 확장될 때도 필요하다. 예를 들어 함수 호출이 깊어지면서 스택이 증가하거나, 동적 메모리 할당으로 힙이 커질 경우 새로운 페이지가 필요하게 되며, 이때도 free frame list에서 프레임이 할당된다.

> free frame list는 가상 메모리 시스템에서 동적으로 발생하는 메모리 요구를 처리하기 위한 자원 관리 메커니즘이다

###  Performance of Demand Paging
Demand Paging의 성능을 분석할 때는 유효 접근 시간(EAT, Effective Access Time) 을 계산한다. 이는 페이지 폴트가 발생할 가능성을 고려한 평균 메모리 접근 시간을 의미한다.

- ma: 한 번의 메모리 접근 시간(memory access time)
- p: 페이지 폴트가 발생할 확률
- EAT = (1 - p) * ma + p * (page fault time)

페이지 폴트가 발생하지 않을 확률(1 − p)에서는 단순히 메모리 접근 시간만 소요되고, 페이지 폴트가 발생할 확률(p)에서는 페이지 폴트를 처리하는 데 걸리는 전체 시간이 추가로 소요된다.

page fault time에는 무엇이 포함될까? 페이지 폴트를 처리하는 데는 크게 세 가지 주요 단계가 있다.
1. 페이지 폴트 인터럽트를 처리하는 시간이다. CPU가 트랩을 발생시키고, 운영체제가 현재 프로세스의 상태를 저장한 뒤 적절한 처리 루틴으로 제어를 넘기는 과정이 포함된다.
2. 필요한 페이지를 보조기억장치에서 읽어오는 시간이다. 이 단계는 디스크 I/O가 포함되므로 일반적인 메모리 접근 시간보다 훨씬 오래 걸린다.
3. 페이지가 메모리에 적재된 후 프로세스를 다시 시작하는 시간이다. 페이지 테이블을 갱신하고, 중단되었던 명령어를 재실행한다.

중요한 점은, 디스크 접근 시간이 매우 크기 때문에 페이지 폴트 확률 p가 아주 작더라도 EAT에 큰 영향을 미친다는 것이다. 따라서 Demand Paging 시스템에서 성능을 유지하려면 페이지 폴트율을 매우 낮게 유지하는 것이 핵심이다.


## Copy-on-Write
Copy-on-Write(COW)는 여러 프로세스가 하나의 페이지를 공유하고 있을 때, 그 페이지에 쓰기(write) 작업이 발생하는 경우에만 실제 복사를 수행하는 기법이다.

단순히 읽기만 하는 동안에는 하나의 물리적 페이지를 계속 공유하고, 어느 한 프로세스가 해당 페이지의 내용을 수정하려는 순간에만 새로운 페이지를 복사하여 독립적인 공간을 할당한다.


이 개념은 프로세스 생성 과정에서 특히 중요한데, 

- 예를 들어 fork() 시스템 호출은 부모 프로세스를 복사하여 자식 프로세스를 생성한다. 이때 부모의 모든 메모리를 즉시 복사한다면 큰 오버헤드가 발생한다. 대신 Copy-on-Write 방식을 사용하면, 부모와 자식은 처음에는 동일한 메모리 페이지를 공유한다. 이후 둘 중 하나가 해당 페이지를 수정하려고 할 때에만 실제 복사가 이루어진다.

- exec() 호출은 현재 프로세스의 메모리 공간을 새로운 프로그램으로 교체한다. 많은 경우 fork() 직후 exec()가 호출되므로, Copy-on-Write를 사용하면 불필요한 메모리 복사를 피할 수 있다. 자식 프로세스가 곧바로 새로운 프로그램으로 대체될 경우, 실제로 페이지를 복사할 필요가 거의 없기 때문이다.

## Page Replacement
멀티프로그래밍의 정도를 높이면 우리는 물리적 메모리를 여러 프로세스에 나누어 주게 되고, 결과적으로 메모리를 과도하게 할당(over-allocation)하는 상황이 발생할 수 있다.

예를 들어, 물리적 메모리에 40개의 프레임이 있고, 각각 10페이지 크기의 프로세스 6개를 실행한다고 가정하자. 이론적으로는 총 60페이지가 필요하지만, 각 프로세스가 실제로는 5페이지씩만 사용한다면 전체 30페이지 정도만 메모리에 올라오게 된다. 이 경우 Demand Paging 덕분에 시스템은 10개의 프레임을 여유로 남겨둘 수 있다.

그러나 문제가 되는 상황은, 갑자기 각 프로세스가 자신의 10페이지 전체를 모두 사용하려 하거나, 추가로 큰 버퍼를 할당하여 더 많은 페이지를 요구하는 경우이다. 이때는 더 이상 사용할 수 있는 free frame이 없게 된다.

이런 경우 운영체제는 **페이지 교체(Page Replacement)** 를 수행해야 한다. 현재 메모리에 올라와 있는 페이지 중 하나를 선택하여 보조기억장치로 내보내고, 그 자리에 새로 필요한 페이지를 적재한다.

이러한 상황이 빈번하게 발생하면, 페이지 폴트가 급격히 증가하고, 대부분의 시간을 페이지 교체에 소비하는 **Thrashing(스래싱)** 상태가 발생할 수 있다. 스래싱이 발생하면 CPU 이용률은 오히려 떨어지고 시스템 성능이 심각하게 저하된다.


Page Replacement는 사용할 수 있는 free frame이 없을 때 수행되는 메모리 관리 기법이다. 빈 프레임이 하나도 없다면, 운영체제는 현재 메모리에 올라와 있는 페이지 중 하나를 선택하여 제거해야 한다.

교체 대상이 될 페이지를 선택한다. 이 페이지는 현재 즉시 사용되지 않는 것으로 판단된 페이지이며, 선택은 특정 페이지 교체 알고리즘(예: FIFO, LRU 등)에 따라 이루어진다.


선택된 페이지가 수정된(dirty) 상태라면
  - 그 내용을 보조기억장치의 스왑 공간(swap space)에 기록해야 한다. 
  - 이후 해당 페이지의 페이지 테이블 항목을 갱신하여, 그 페이지가 더 이상 메모리에 존재하지 않음을 나타내도록 invalid로 표시한다.

프레임이 비워지면, 페이지 폴트가 발생했던 프로세스가 필요로 하는 새로운 페이지를 그 프레임에 적재한다. 적재가 완료되면 페이지 테이블을 다시 갱신하고, 중단되었던 명령어 실행을 재개한다.

> 이 과정은 메모리가 가득 찬 상황에서도 시스템이 계속 동작할 수 있도록 해주지만, 교체가 빈번해지면 성능 저하가 발생할 수 있으므로 효율적인 교체 정책이 매우 중요하다.

### Page Fault Service Routine including Page Replacement
Page Replacement가 포함된 Page Fault 처리 절차는 다음과 같이 진행된다.

1. 운영체제는 보조기억장치에서 요구된 페이지가 저장되어 있는 위치를 찾는다. 페이지 폴트가 발생했으므로, 해당 페이지는 현재 물리적 메모리에 존재하지 않는 상태이다.

2. 사용할 수 있는 free frame이 있는지 확인한다. 만약 빈 프레임이 있다면 이를 그대로 사용하면 된다. 
   - free frame이 없다면, 페이지 교체 알고리즘을 이용하여 희생 페이지(victim page)가 들어 있는 프레임을 선택해야 한다. 
   - 선택된 페이지가 수정된 상태(dirty)라면 그 내용을 보조기억장치에 기록한 뒤, 
   - 페이지 테이블과 프레임 테이블을 갱신하여 해당 페이지가 더 이상 메모리에 존재하지 않음을 표시한다.

3. 프레임이 확보되면, 
   - 보조기억장치에 있던 요구된 페이지를 새로 확보된 프레임으로 읽어온다. 
   - 이후 페이지 테이블과 프레임 테이블을 수정하여 이 페이지가 현재 메모리에 적재되었음을 나타낸다. valid 비트도 함께 갱신된다.

4. 모든 작업이 완료되면, 페이지 폴트로 인해 중단되었던 명령어부터 다시 실행을 계속한다.

### Two major problems to implement demand paging
1. 프레임 할당 알고리즘(Frame-Allocation Algorithm): 각 프로세스에 몇 개의 프레임을 할당할 것인지 결정하는 문제이다. 너무 적게 할당하면 페이지 폴트가 자주 발생하여 성능이 저하되고, 너무 많이 할당하면 다른 프로세스가 사용할 수 있는 메모리가 줄어들어 시스템 전체 효율이 떨어질 수 있다.

2. 페이지 교체 알고리즘(Page-Replacement Algorithm): 메모리가 가득 찼을 때 어떤 페이지를 희생 페이지(victim page)로 선택하여 교체할 것인지를 결정해야 한다. 이 선택이 비효율적이면 페이지 폴트가 급격히 증가하고, 시스템 성능이 크게 저하될 수 있다. 따라서 가능한 한 앞으로 사용될 가능성이 낮은 페이지를 선택하는 것이 중요하다.


특히 보조기억장치 I/O는 메모리 접근에 비해 매우 비용이 크기 때문에, Demand Paging 기법에서 작은 성능 개선만 이루어져도 전체 시스템 성능에는 매우 큰 향상이 나타날 수 있다. 따라서 프레임 할당과 페이지 교체 정책의 설계는 가상 메모리 시스템에서 매우 중요한 요소라고 할 수 있다.


### Evaluation of Page Replacement Algorithms
페이지 교체 알고리즘을 평가하기 위해서는 먼저 reference string(참조 문자열) 이 필요하다. 참조 문자열이란, 프로그램이 실행되는 동안 접근한 페이지 번호들의 순서를 나열한 것이다. 메모리 접근 패턴을 시간 순서대로 기록한 것이다.

페이지 교체 알고리즘의 성능은 이 참조 문자열을 기반으로 평가된다. 특정 알고리즘을 선택한 뒤, 주어진 reference string에 대해 시뮬레이션을 수행하고 그 과정에서 발생하는 페이지 폴트의 횟수를 계산한다. 일반적으로 페이지 폴트의 수를 최소화하는 알고리즘이 더 좋은 알고리즘으로 평가된다.

페이지 프레임의 개수도 중요한 요소이다. 일반적으로 사용할 수 있는 프레임 수가 많을수록 더 많은 페이지를 메모리에 유지할 수 있으므로 페이지 폴트의 발생 횟수는 감소한다. 그러나 시스템 전체 메모리는 한정되어 있으므로, 한 프로세스에 많은 프레임을 할당하면 다른 프로세스에 할당할 수 있는 프레임이 줄어들 수 있다. 가능한 한 적은 페이지 폴트를 발생시키는 방향으로 설계하는 것이 목표이다.

### FIFO Page Replacement
FIFO(First-In-First-Out) 페이지 교체 알고리즘은 가장 단순한 페이지 교체 방법이다. 이 알고리즘은 메모리에 가장 먼저 들어온 페이지를 가장 먼저 교체하는 방식으로 동작한다. 즉, 페이지가 메모리에 적재된 순서를 기준으로 큐(queue)를 유지하고, 교체가 필요할 때 가장 오래된(가장 먼저 들어온) 페이지를 희생 페이지로 선택한다.

동작 방식은 비교적 단순하다. 페이지가 메모리에 들어올 때 큐의 뒤에 추가되고, 교체가 필요하면 큐의 앞에 있는 페이지를 제거한다. 구현이 쉽고 관리 비용이 적다는 장점이 있지만, 오래되었더라도 앞으로 자주 사용될 페이지를 교체할 수 있다는 단점이 있다.

#### Belady’s Anomaly
Belady’s Anomaly는 페이지 프레임의 개수를 늘렸음에도 불구하고 페이지 폴트가 오히려 증가하는 현상을 말한다. 일반적으로는 프레임 수가 많아질수록 더 많은 페이지를 메모리에 유지할 수 있으므로 페이지 폴트는 감소해야 한다고 생각한다. 그러나 FIFO(First-In-First-Out)와 같은 일부 페이지 교체 알고리즘에서는 이러한 직관이 항상 성립하지 않는다.

> FIFO는 이해와 구현은 쉽지만, 성능 면에서는 더 정교한 알고리즘들(LRU, Optimal 등)에 비해 비효율적일 수 있다.

### Optimal Page Replacement (OPT, MIN)
Optimal Page Replacement는 이론적으로 가장 낮은 페이지 폴트율을 보장하는 알고리즘이다. 이 알고리즘은 Belady’s Anomaly가 발생하지 않으며, 모든 페이지 교체 알고리즘 중 최상의 성능을 기준(reference standard)으로 제공한다.

- 앞으로 가장 오랫동안 사용되지 않을 페이지를 교체한다.

즉, 현재 시점 이후의 참조 문자열을 모두 알고 있다고 가정하고, 가장 먼 미래에 다시 사용되거나 아예 사용되지 않을 페이지를 선택해 교체한다. 이렇게 하면 앞으로 발생할 페이지 폴트를 최소화할 수 있다.

OPT는 항상 가능한 최소의 페이지 폴트 수를 보장하지만, 실제 시스템에서는 구현이 불가능하다. 그 이유는 미래의 메모리 참조 패턴을 미리 알 수 없기 때문이다. 

> OPT는 실제 운영체제에서 직접 사용되기보다는, 다른 알고리즘(FIFO, LRU 등)의 성능을 비교하는 기준으로 사용된다.


### LRU Page Replacement
> Shortest-Job-First(SJF) CPU 스케줄링에서 SJF는 앞으로 가장 짧게 실행될 작업을 선택하는 방식으로, 이론적으로 평균 대기 시간을 최소화한다. 하지만 실제로는 각 작업의 미래 실행 시간을 정확히 알 수 없다는 한계가 있다. 
> 
> Optimal Page Replacement(OPT)도 이와 유사하게, 앞으로 가장 오랫동안 사용되지 않을 페이지를 교체함으로써 페이지 폴트를 최소화하지만, 미래의 참조 패턴을 알아야 한다는 점에서 현실적으로 구현이 어렵다.
>
> FIFO와 OPT의 핵심적인 차이는 관점에 있다. FIFO는 과거를 기준으로 판단한다. 즉, “가장 먼저 들어온 페이지”를 교체한다. 반면 OPT는 미래를 기준으로 판단한다. 즉, “앞으로 가장 늦게 사용될 페이지”를 교체한다. 하나는 과거를 보고 결정하고, 다른 하나는 미래를 보고 결정한다는 점이 본질적인 차이이다.
> 
> 미래를 정확히 알 수 없다면 어떻게 해야 할까? 한 가지 방법은 최근의 과거(recent past)를 가까운 미래의 근사치로 사용하는 것이다. **실제 프로그램은 참조의 지역성(Locality of Reference)을 가지므로, 최근에 사용된 페이지는 가까운 미래에도 다시 사용될 가능성이 높다.**
>
> 아이디어에 기반한 알고리즘이 바로 **LRU(Least Recently Used)** 이다. LRU는 가장 오랫동안 사용되지 않은 페이지를 교체한다. 즉, 과거의 사용 기록을 바탕으로 미래의 사용 가능성을 예측하는 방식이다. LRU는 OPT를 직접 구현할 수는 없지만, 그에 대한 현실적인 근사(approximation)로서 널리 사용되는 알고리즘이다.


LRU(Least Recently Used) 페이지 교체 알고리즘은 가장 오랫동안 사용되지 않은 페이지를 교체하는 방식이다. 이 알고리즘은 참조의 지역성(Locality of Reference)에 기반하여, 최근에 사용된 페이지는 가까운 미래에도 다시 사용될 가능성이 높다고 가정한다.

LRU는 각 페이지에 대해 “마지막으로 사용된 시점”을 기록한다. 그리고 교체가 필요할 때, 가장 오랜 시간 동안 참조되지 않은 페이지를 선택하여 제거한다. 즉, 과거의 사용 기록을 이용해 미래의 사용 가능성을 예측하는 방식이다.

LRU는 스택 성질(stack property) 을 만족하기 때문에, 프레임 수가 증가하면 페이지 폴트 수가 증가하지 않는다. 따라서 Belady’s Anomaly가 발생하지 않는다는 장점도 가진다.

> stack property: 프레임 수가 늘어나면, 기존에 들어있던 페이지들은 항상 그대로 포함된다.
>
> - 메모리 프레임이 k개일 때 들어있는 페이지 집합은 프레임이 k+1개일 때의 페이지 집합의 부분집합(subset) 이 된다.
> 
> 최근 사용 순서가 명확하게 전역적으로 정렬되어 있기 때문에 Belady’s Anomaly가 발생하지 않는다.

LRU(Least Recently Used) 정책은 성능이 우수한 편으로 평가되며 실제 시스템에서 자주 사용되는 페이지 교체 기법이다. 참조의 지역성(Locality of Reference)에 기반하여, 가장 오랫동안 사용되지 않은 페이지를 교체함으로써 비교적 낮은 페이지 폴트율을 기대할 수 있다.

그러나 LRU를 구현하는 데에는 한 가지 중요한 문제가 있다. 바로 각 프레임을 “마지막 사용 시점”에 따라 정확히 정렬해야 한다는 점이다. **어떤 페이지가 가장 오랫동안 사용되지 않았는지를 판단하려면 모든 페이지의 최근 사용 정보를 추적해야 한다.** 이를 소프트웨어만으로 처리하면 오버헤드가 커질 수 있으므로, 상당한 하드웨어 지원이 필요할 수 있다.

### Two implementation methods for the LRU
1. Counter: 각 페이지 테이블 엔트리에 시간 정보를 저장해 두고, 페이지가 참조될 때마다 현재 시간을 기록한다. 교체가 필요할 때는 가장 오래된 시간 값을 가진 페이지를 선택한다. 이 방식은 직관적이지만, 하드웨어 차원의 시간 기록 기능이 필요하다.

2. Stack: 페이지를 최근 사용 순서대로 스택에 유지하며, 어떤 페이지가 참조될 때마다 그 페이지를 스택의 맨 위로 이동시킨다. 가장 아래에 있는 페이지가 가장 오랫동안 사용되지 않은 페이지가 된다. 이 방법은 정확한 LRU를 구현할 수 있지만, 관리 비용이 클 수 있다.


### LRU-Approximation
LRU는 이상적으로 구현하려면 각 페이지의 “마지막 사용 시점”을 정확히 추적해야 하므로 상당한 하드웨어 지원이 필요하다. 그러나 많은 시스템에서는 완전한 LRU 대신, 이를 근사(approximation)하는 방식을 사용한다. 그 대표적인 방법이 reference bit(참조 비트) 를 이용하는 방식이다.

참조 비트는 각 페이지에 하나씩 연결된 비트로, 초기값은 0이다. 어떤 페이지가 CPU에 의해 참조되면 하드웨어가 자동으로 해당 페이지의 reference bit를 1로 설정한다. 운영체제는 주기적으로 이 비트를 검사하여 페이지의 최근 사용 여부를 판단한다.

페이지 교체가 필요할 때, reference bit가 0인 페이지가 있다면 그것을 교체 대상으로 선택한다. **reference bit가 0이라는 것은 최근 일정 시간 동안 사용되지 않았다는 의미이므로, LRU의 “오랫동안 사용되지 않은 페이지”라는 개념을 어느 정도 근사하게 된다.**

이 방식은 완전한 LRU처럼 정확하지는 않지만, 구현 비용이 훨씬 낮고 하드웨어 지원도 단순하다는 장점이 있다. 따라서 실제 운영체제에서는 reference bit를 활용한 다양한 LRU 근사 알고리즘(예: Second-Chance, Clock 알고리즘 등)이 널리 사용된다.


> Second-Chance 알고리즘
>
> Second-Chance 알고리즘은 FIFO 페이지 교체 방식을 개선한 방법이다. 이 알고리즘에서는 각 페이지에 참조 비트(reference bit) 를 두어, 페이지가 최근에 사용되었는지를 기록한다. 페이지가 메모리에서 참조되면 해당 페이지의 참조 비트는 1로 설정된다.
>
> 페이지 교체가 필요할 때는 FIFO처럼 가장 오래된 페이지부터 검사한다. 이때 참조 비트가 0이면 그 페이지를 바로 교체하고, 참조 비트가 1이면 이를 0으로 바꾸고 페이지를 큐의 뒤로 보내어 한 번 더 기회를 준다. 즉, 최근에 사용된 페이지는 즉시 교체하지 않고 한 번 더 보호해 주는 방식이다.

> Clock 알고리즘
> 
> Clock 알고리즘은 Second-Chance 알고리즘을 원형 큐 형태로 구현한 방식이다. 페이지들은 원형 구조로 배열되어 있으며, 이를 가리키는 포인터(시계 바늘)가 존재한다.
>
> 페이지 교체가 필요하면 포인터가 가리키는 페이지의 참조 비트를 확인한다. 참조 비트가 0이면 해당 페이지를 교체하고, 1이면 이를 0으로 변경한 뒤 포인터를 다음 페이지로 이동시킨다. 이러한 과정을 반복하여 참조 비트가 0인 페이지를 찾으면 교체를 수행한다.

## Allocation of Frames
Frame Allocation 문제는 여러 프로세스가 동시에 실행될 때, 제한된 물리적 프레임을 어떻게 나누어 줄 것인가에 대한 문제이다.

> 예를 들어, 전체 시스템에 128개의 프레임이 있다고 가정하자. 이 중 운영체제(OS)가 35개를 사용하면, 사용자 프로세스가 사용할 수 있는 프레임은 93개가 남는다. Pure Demand Paging을 사용한다면, 이 93개의 프레임은 free-frame list에 들어가게 된다.
>
> 초기에는 페이지 폴트가 발생할 때마다 빈 프레임이 하나씩 할당되므로, 처음 93번의 페이지 폴트는 단순히 free frame을 사용하는 것으로 해결된다. 그러나 94번째 페이지 폴트부터는 더 이상 빈 프레임이 없기 때문에 페이지 교체(Page Replacement)가 필요하게 된다.
> 
> 이제 두 개의 프로세스가 동시에 실행된다고 가정해 보자. 문제는 남은 93개의 프레임을 두 프로세스에 어떻게 배분할 것인가이다. 한 프로세스에 너무 많은 프레임을 주면 다른 프로세스는 부족한 프레임 때문에 잦은 페이지 폴트를 겪게 될 수 있다. 반대로 균등하게 나누어 주더라도 각 프로세스의 특성이나 필요 메모리 양이 다를 수 있으므로 항상 최적의 성능을 보장하지는 못한다.


프레임 할당에는 여러 전략이 존재한다. 

- 예를 들어, 모든 프로세스에 동일한 수의 프레임을 할당하는 균등 할당(equal allocation) 방식이 있고, 
- 프로세스의 크기(페이지 수)에 비례하여 나누어 주는 비례 할당(proportional allocation) 방식도 있다. 
- 또한 페이지 교체를 각 프로세스 내부에서만 수행하는지(local replacement), 
- 아니면 전체 프로세스를 대상으로 수행하는지(global replacement)에 따라서도 성능이 달라진다.

> Frame Allocation 문제는 제한된 메모리를 여러 프로세스에 공정하고 효율적으로 분배하여, 전체 시스템 성능을 최적화하는 것을 목표로 하는 중요한 설계 문제이다.

### The strategies for frame allocation
프레임 할당 전략(Frame Allocation Strategies)은 제한된 물리적 메모리를 여러 프로세스에 어떻게 나누어 줄 것인지 결정하는 방법이다.

1. Equal vs. Proportional
    - Equal Allocation(균등 할당) 은 모든 프로세스에 동일한 수의 프레임을 나누어 주는 방식이다. 예를 들어 90개의 프레임과 3개의 프로세스가 있다면, 각 프로세스에 30개씩 할당한다. 구현이 단순하고 공정해 보이지만, 각 프로세스의 크기나 특성을 고려하지 않기 때문에 비효율적일 수 있다.
    
    - Proportional Allocation(비례 할당) 은 각 프로세스의 크기(페이지 수)에 비례하여 프레임을 할당하는 방식이다. 더 큰 프로세스에는 더 많은 프레임을 주고, 작은 프로세스에는 적은 프레임을 준다. 이는 메모리 요구량을 더 현실적으로 반영할 수 있어 일반적으로 더 효율적이다.

2. Global vs. Local (페이지 교체 범위)
    - Local Replacement(지역 교체) 는 한 프로세스에 할당된 프레임 집합 내에서만 교체를 수행하는 방식이다. 즉, 다른 프로세스의 프레임은 건드리지 않는다. 이 방식은 각 프로세스의 성능이 비교적 독립적으로 유지된다는 장점이 있다.
    
    - Global Replacement(전역 교체) 는 시스템 전체 프레임 집합을 대상으로 교체를 수행한다. 즉, 한 프로세스가 다른 프로세스의 프레임을 빼앗을 수도 있다. 이 방식은 전체 시스템 성능을 높일 수 있지만, 어떤 프로세스는 갑자기 프레임을 잃어 성능이 급격히 저하될 위험도 있다.


## Thrashing
Thrashing은 프로세스가 실제 작업을 수행하기보다 페이지를 계속해서 메모리와 보조기억장치 사이에서 교환(swapping)하는 데 대부분의 시간을 소비하는 상태를 말한다. CPU는 거의 유휴 상태에 가깝고, 시스템은 페이지를 들여오고 내보내는 작업에 과도하게 집중하게 된다.

이 현상은 **주로 프로세스에 할당된 프레임 수가 충분하지 않을 때 발생한다.** 프로세스가 실행에 필요한 최소한의 페이지 집합(working set)을 유지하지 못하면, 조금만 실행해도 새로운 페이지가 필요해지고, 그때마다 페이지 폴트가 발생한다. 결과적으로 페이지 폴트율(page-fault rate)이 매우 높아진다.

페이지 폴트가 빈번해지면 디스크 I/O가 급격히 증가하고, CPU 이용률은 오히려 떨어진다. 운영체제는 CPU 사용률이 낮다고 판단해 멀티프로그래밍 정도를 더 높일 수 있는데, 이는 메모리를 더욱 분산시켜 상황을 악화시키고, 결국 시스템 전체가 심각한 성능 저하 상태에 빠질 수 있다.

Thrashing을 방지하기 위해서는 각 프로세스에 충분한 프레임을 보장하거나, Working-Set 모델이나 Page-Fault Frequency(PFF) 같은 기법을 사용하여 메모리 할당을 동적으로 조절해야 한다.

### Working-Set Model
Working-Set Model은 프로그램이 참조의 지역성(locality) 을 가진다는 가정에 기반한 메모리 관리 모델이다. 즉, 어떤 시점에서 프로세스는 전체 페이지를 사용하는 것이 아니라, 일정한 부분 집합만 집중적으로 사용한다는 아이디어에서 출발한다.

이 모델에서는 Δ(델타) 라는 매개변수를 사용하여 working-set window를 정의한다. Δ는 “최근 얼마만큼의 참조를 고려할 것인가”를 나타내는 값이다. 운영체제는 가장 최근 Δ개의 페이지 참조를 조사하고, 그 안에 포함된 서로 다른 페이지들의 집합을 그 시점의 working set(작업 집합) 이라고 정의한다.

working set은 “최근 Δ번의 참조 동안 사용된 페이지들의 집합”이다. 만약 어떤 페이지가 현재 활발히 사용되고 있다면, 최근 참조 기록에 포함되어 있으므로 working set 안에 존재하게 된다. 반대로 더 이상 사용되지 않는 페이지는 시간이 지나면서 최근 Δ개의 참조 범위에서 벗어나게 되고, 결국 working set에서 제거된다.

이 모델의 핵심 목적은 프로세스가 실행에 실제로 필요로 하는 최소한의 페이지 집합을 파악하는 것이다. 만약 프로세스에 할당된 프레임 수가 그 working set 크기보다 작다면 페이지 폴트가 급증하여 thrashing이 발생할 수 있다. 따라서 시스템은 각 프로세스의 working set 크기를 유지할 수 있도록 충분한 프레임을 할당해야 한다.
