## Synchronization Tools
임계구역 문제를 해결하기 위해 **고수준 소프트웨어 동기화 도구(Higher-level software tools)** 가 사용된다. 

- Mutex Lock(뮤텍스 락): 단순한 동기화 도구이다. 하나의 락을 획득한 프로세스만이 임계구역이 들어갈 수 있으며 작업이 끝나면 락을 해제한다. 구조가 단순하고 이해하기 쉽지만, 잘못 사용하면 교착상태나 기아가 발생할 수 있다.

- Semaphore(세마포어): 뮤텍스보다 더 일반적이고 강력하다. 세마포어는 정수 값을 사용하여 여러 개의 자원에 대한 접근을 제어할 수 있으며, 대기와 신호(wait, signal) 연산을 통해 프로세스 간의 동기화를 수행한다. 자원 관리와 순서 제어에 모두 활용할 수 있다.

- Monitor(모니터): 뮤텍스와 세마포어의 단점을 보완하기 위해 등장한 개념이며 공유 데이터와 그에 대한 연산을 하나의 구조 안에 캡슐화하고 동시에 하나의 프로세스만 내부에서 실행되도록 자동으로 보장한다. 또한 조건 변수를 통해 보다 안전하고 체계적인 동기화를 지원한다.

- Liveness(활성 보장): 동기화 설계에서 중요한 개념으로 프로세스가 무한히 기다리지않고 결국에는 진행(progress)할 수 있도록 보장하는 성질을 의미한다. 이는 교착상태나 기아 상태가 발생하지 않도록 시스템이 설계되어야 함을 뜻한다.




## Mutex Lock
mutex는 **mutual exclusion(상호 배제)**의 줄임말로, 임계구역에 동시에 둘 이상의 프로세스가 들어가지 못하도록 하기 위한 동기화 도구이다. 뮤텍스의 목적은 임계구역을 보호하고 Race Condition을 방지하는 것이다. 공유 데이터를 접근하는 코드 영역을 하나의 lock으로 감싸 두고 한 번에 하나의 프로세스만 해당 영역을 실행하도록 제한한다.

어떤 프로세스가 임계구역에 들어가려면 먼저 lock을 획득해야한다. 만약 다른 프로세스가 이미 락을 가지고 있다면 현재 프로세스는 락이 해제될 때까지 기다려야 한다. 그리고 임계구역에서의 작업이 끝나면 반드시 lock을 해제하여 다른 프로세스가 들어올 수 있도록 해야한다.

뮤텍스 락은 available과 acquire(), release()로 구성된다. 
1. available 변수는 현재 락이 사용 가능한 상태 여부를 나타낸다. 
    - available = true이면, 락이 비어 있어 임계구역에 들어갈 수 있음을 의미한다. 
    - available = false이면, 이미 다른 프로세스가 락을 획득한 상태이므로 들어갈 수 없다.

2. acquire() 함수는 임계구역에 들어가기 전에 호출된다. available이 true인지 확인하고 만약 사용 가능하다면 이를 false로 바꾸어 락을 획득한다. 이미 false라면 락이 해제될 때까지 기다린다.

3. release() 함수는 임계구역을 빠져나올 때 호출된다. 이 함수는 available을 true로 설정하여 다른 프로세스가 락을 획득할 수 있도록 한다.

acquire, release 모두 원자적으로 수행되어야 한다. 두 연산이 원자적으로 실행되지 않는다면 여러 프로세스가 동시에 available 값을 확인하고 수정하는 과정에서 또 다른 Race Cond.이 발생할 수 있다. 그렇기 때문에 이 두 함수는 하드웨어가 제공하는 원자 명령어를 사용해 구현된다(compare_and_swap())


### Busy waiting
Busy waiting은 뮤텍스 락과 같은 동기화 기법에서 발생할 수 있는 문제이다. 어떤 프로세스가 임계구역에 들어라겨 하지만 이미 다른 프로세스가 락을 보유하고 있는 경우 해당 프로세스는 acquire() 함수 안에서 락이 해제될 때까지 계속해서 확인 loop를 돌게된다. 이를 spinlock이라고 한다.

일반적인 락에서는 대기 중인 스레드를 sleep 상태로 전환시키고, 다른 스레드를 실행시키기 위해 context switch가 발생한다. Context switch는 CPU가 현재 실행 중인 작업의 상태를 저장하고 다른 작업의 상태를 복원하는 과정으로, 일정한 시간과 비용이 필요하다.

하지만 spinlock은 대기 중에 context switch를 발생시키지 않는다. 대신 스레드가 CPU를 점유한 채로 계속해서 락이 풀리기를 기다린다. 이 때문에 임계 구역의 실행 시간이 매우 짧은 경우에는 오히려 더 효율적일 수 있다. 잠깐 기다리기 위해 sleep과 wake-up을 반복하는 것보다, 잠시 동안 CPU를 사용하며 기다리는 것이 더 빠를 수 있기 때문이다.

(CPU를 점유하며 대기하는 시간보다 문맥교환이 더 큰 비용이 들어가는 경우 -> 대기 시간이 아주 짧은 경우 계속 대기시키는 것이 유리하다는 뜻)


## Semaphore
세마포어는 정수형 변수 S로 정의되며, 초기화를 제외하고는 오직 두 개의 표준 원자적(atomic) 연산을 통해서만 접근할 수 있다. 그 두 연산은 wait() 와 signal() 이며, 경우에 따라 각각 P() 와 V() 라고도 불린다.

세마포어의 정수 값에 대한 모든 변경은 wait(), signal() 연산 내부에서 반드시 원자적으로 수행되어야 한다. 이 두 연산이 실행되는 동안에는 다른 프로세스나 스레드가 끼어들어 세마포어 값을 동시에 변경할 수 없어야 한다. 그래야만 세마포어가 임계 구역 보호라는 목적을 정확하게 수행할 수 있다.


## Binary Semaphore와 Counting Semaphore
Binary Semaphore는 값의 범위가 0과 1만 가능한 세마포어이다.
자원이 사용 중이면 0, 사용 가능하면 1의 값을 가지며, 한 번에 하나의 프로세스(또는 스레드)만 임계 구역에 들어갈 수 있도록 제어한다. 이런 점에서 동작 방식이 mutex lock과 매우 유사하다.

반면에 Counting Semaphore는 값의 범위가 0과 1에 제한되지 않고, 0 이상의 정수 전체 범위를 가질 수 있다.
이 세마포어는 동시에 여러 개가 존재하는 자원을 관리할 때 사용된다. 예를 들어 동일한 자원이 5개 있다면, 세마포어의 초기값을 5로 설정해 두고 자원을 사용할 때마다 wait()로 값을 감소시키고, 반환할 때 signal()로 값을 증가시킨다.

따라서 Binary Semaphore는 하나의 자원을 보호할 때,<br>
Counting Semaphore는 여러 개의 동일한 자원을 관리할 때 적합하다.

## Counting Semaphore
Counting semaphore을 사용하는 방법은 다음과 같다. 먼저, 세마포어의 초기값을 사용 가능한 자원의 개수로 설정한다. 이 값은 현재 이용할 수 있는 자원의 수를 의미한다. 어떤 프로세스가 자원을 사용하려고 하면 wait() 연산을 호출하며, 이 연산은 세마포어 값을 1 감소시킨다. 값이 감소했다는 것은 자원 하나가 사용 중임을 의미한다. 

프로세스가 자원 사용을 마치고 반납할 때는 signal() 연산을 호출하며, 이 연산은 세마포어 값을 1 증가시킨다. 이는 자원이 다시 사용 가능 상태가 되었음을 나타낸다.

만약 세마포어 값이 0이 되면, 모든 자원이 사용 중이라는 뜻이다. 이때 추가로 자원을 사용하려는 프로세스는 즉시 진행하지 못하고 대기(block) 상태가 된다. 이후 다른 프로세스가 signal()을 호출하여 세마포어 값이 1 이상이 되면, 대기 중이던 프로세스가 다시 실행되어 자원을 사용할 수 있게 된다.


### Using the semaphore to solve synchronization problem
세마포어를 이용해 동기화 문제를 해결해야하는 상황이 있다. 두 개의 프로세스 P1, P2가 동시에 실행되고 P1에는 S1, P2에는 S2가 있다. S2가 S1 이후에 실행되어야한다고 가정한다. 실행 순서를 보장해야하는 상황이다.

두 프로세스는 synch라는 세마포어를 공유하며 0으로 초기화 한다.

𝑃1은 𝑆1을 수행한 뒤 signal(synch)를 호출한다. > 세마포어 값이 1 증가한다.

𝑃2는 𝑆2를 실행하기 전에 wait(synch)를 호출한다. > 세마포어 값이 0이면 대기하고, 1 이상이면 1 감소시키고 실행을 계속한다.

초기값이 0이므로 P2가 먼저 실행되어 wait(synch)를 호출하면 세마포어 값이 0이기 때문에 P2는 대시 상태로 들어간다. 이후 P1이 S1을 실행하고 signal(synch)를 호출하면 세마포어 값이 1이 되고 대기중인 P2가 깨어나 S2를 실행하게 된다.


## Semaphore Implementation
뮤텍스 락이나 세마포어에서 busy waiting에 대한 문제가 발생할 수 밖에 없고 spinlock으로 활용할 수 있지만 P(wait)와 V(signal) 연산을 수정하여 극복할 수 있다.

어떤 프로세스가 wait()를 실행 했을 때 사용할 수 있는 자원이 없다면 대기하며 반복 확인하지 않고 스스로를 suspend 상태로 전환 후 waiting queue로 들어간다.

이후 다른 프로세스가 작업을 마치고 signal() 연산을 실행하여 세마포어 값을 증가시키고 waiting queue에 있는 프로세스 하나를 재시작 시켜 ready queue로 이동시키면 스케줄러에 의해 다시 CPU를 할당받아 실행을 이어갈 수 있다.

 - wait()에서 자원이 없으면 바쁜 대기 대신 블록(block) 상태로 전환하고
 - signal()에서 대기 중인 프로세스를 깨워 실행 가능 상태로 복귀시킨다.

```
typeof struct{
    int value;
    struct process *list;
} semaphore

wait(semaphore *S){
    S-> value--;
    if(S->value < 0){
        add this process to S->list;
        sleep() //  waiting queue로 들어가는 부분
    }
}

signal(semaphore *S){
    S->value++;
    if(S->value <= 0){
        remove a process P fron S->list;
        wakeup(P); // ready queue로 이동
    }
}
```

## Monitors
세마포어는 편리하고 효과적인 동기화 도구이나 특정한 실행 순서에서만 나타나는 비결정적인 특성을 가지고 있고 디버깅이 매우 어렵다. 세마포어는 강력하지만 사용자가 직접 wait, signal의 위치와 순서를 정확히 설계해야하므로 논리적 실수가 발생하기 쉽고 오류를 발견하기도 쉽지 않다.

이런 문제를 해결하는 방법으로는 동기화 도구를 고수준 언어 구조로 통합하는 것이다. 그 대표적인 예가 모니터(monitor) 이다. 모니터는 하나의 고수준 동기화 구조로, 공유 데이터와 그 데이터를 조작하는 연산을 하나의 추상화된 단위로 묶는다. 그리고 한 번에 하나의 프로세스(또는 스레드)만 모니터 내부에 들어올 수 있도록 자동으로 상호 배제를 보장한다.


### Monitor type
모니터 타입은 추상자료형의 한 형태로 프로그래머가 정의한 여러 함수들을 포함하며 이 함수들은 모니터 내부에서 자동으로 상호 배제가 보장된다. 한 번에 하나의 프로세스만 모니터 안에서 실행될 수 있다.

모니터는 해당 타입의 상태를 정의하는 변수들을 선언하며 이 변수들은 모니터 내부에 캡슐화되어 외부에서 직접 접근 할 수 없다. 그리고 이 변수들을 조작하는 함수들의 본문도 함께 정의된다.

모니터는 
- 상태를 나타내는 변수들
- 그 변수를 조작하는 연산들
- 그리고 자동으로 보장되는 상호 배제

를 하나의 단위로 묶은 고수준 동기화 구조이다. 이를 통해 공유 데이터에 대한 접근을 구조적으로 안전하게 관리할 수 있다.

### Condition Variable
모니터만으로는 표현하기 어려운 동기화 상황을 해결하기 위해 도입된 개념이다.

모니터는 기본적으로 상호 배제를 자동으로 보장해 주지만 특정 조건이 만족될 때까지 기다려야 하는 상황까지 직접 처리해 주지는 못한다. 이런 상황을 위해 조건 변수를 정의하여 어떤 조건이 충족될 때까지 프로세스를 대기시키고 그 조건이 만족되었을 때 다시 실행을 재개하도록 하는 추가적인 동기화 메커니즘을 제공한다.


##  Java Monitors
자바에서는 스레드 동기화를 위해 모니터와 유사한 동시성 메커니즘을 제공하는데 이를 모니터 락(monitor lock) 또는 내재적 락(intrinsic lock) 이라고 한다.

Java의 모든 객체는 내부적으로 하나의 모니터 락을 가지며 특정 스레드가 그 객체의 락을 획득하면 다른 스레드는 해당 락이 해제될 때까지 진입할 수 없다. 이를 통해 상호 배제(mutual exclusion)가 자동으로 보장된다.

Java 동기화를 위한 기본 언어 구성 요소는 다음과 같다.

- synchronized 키워드:
메서드나 코드 블록에 사용되며, 해당 객체의 모니터 락을 획득한 스레드만 그 영역을 실행할 수 있도록 한다. 즉, 임계 구역을 보호하는 역할을 한다.

- wait()와 notify() 메서드:
wait()는 현재 스레드를 대기 상태로 전환하면서 모니터 락을 반납한다.
notify()는 같은 객체에서 wait()로 대기 중인 스레드 중 하나를 깨운다.
(여러 스레드를 모두 깨우는 notifyAll()도 존재한다)



## Liveness
Liveness(활성성)는 프로세스들이 실행 과정에서 결국에는 계속 진행할 수 있도록 시스템이 만족해야하는 성질들의 집합을 의미한다. 단순히 상호 배제만 보장하는 것이 아니라 프로세스가 영원히 멈춰있지 않고 언젠가는 실행을 계속할 수 있어야 한다는 개념이다.

임계 구역 문제에서 중요한 두 가지 조건 progress(진행)와 bounded waiting(유한 대기)이다. 세마포어나 모니터를 사용하더라도 이를 잘못 설꼐하면 이러한 요구 사항을 보장하지 못할 수 있다. 즉, 동기화 도구가 존재한다고 해서 Liveness가 보장되는 것은 아니다.

활성성 실패(liveness failure)를 일으키는 대표적인 두 가지 상황은 다음과 같다.

- Deadlock(교착 상태): 두 개 이상의 프로세스가 서로가 가진 자원을 기다리면서 영원히 진행하지 못하는 상태이다.
- Priority Inversion(우선순위 역전): 낮은 우선순위의 프로세스가 높은 우선순위 프로세스가 필요로 하는 자원을 점유하고 있어, 결과적으로 높은 우선순위 프로세스의 실행이 지연되는 현상이다.
